4 · Trainer-side metric anatomy — why the perf/* families moved

Side-by-side wandb panels show the post-sync runs (purple) with lower actor_train_tok_per_s/actor_train_tflops, higher actor_train_time, lower wait_time_ratio and (async pair) much lower data_preprocess_time — while end-to-end speed improved. All of it reduces to one semantic change plus one env-generation artifact. Definitions first (code anchors in miles/backends/megatron_utils/actor.py and miles/utils/train_metric_utils.py):

metricdefinition (what the timer actually wraps)
perf/train_wait_timeInverse timer: accumulates whenever the actor is outside the train block — idle waiting for the next staleness-admissible batch plus data fetch/preprocess and iterator build.
perf/data_preprocess_timeget_rollout_data(): ray.get of this rank's DP shard (includes cross-node object transfer of the image-heavy payload) + host→GPU moves of tokens/masks/multimodal tensors/OPD targets. Counted inside train_wait, not train.

The alternative HFU convention (hardware-FLOPs) would use 4 under full recompute.

Root cause 1 — activation recomputation is now actually on

Both recipes have always requested --recompute-granularity full --recompute-method uniform --recompute-num-layers 1. On the bridge (megatron_to_hf_mode=bridge) path the pre-sync code silently dropped those flags before they reached the provider; upstream #1483's _apply_bridge_runtime_config — merged in this sync — propagates them (its own comment: “activation recompute (silently dropped before → no checkpointing → OOM at long context)”). So the pre-sync purple-vs-brown gap is no-recompute vs full-recompute, not an efficiency loss. Evidence chain:

  • The 4/3 signature: full recompute re-runs the forward during backward — ideal cost goes from 3 forward-equivalents (1F+2F) to 4 → time ×1.33, tok/s and tflops ×0.75. Measured: actor_train_time ×1.32 (async) and ×1.325 (OPD); tok/s ×0.765 / tflops ×0.766 (async).
  • The forward-only control: log_probs_time is a pure forward pass and recompute cannot touch it — it is unchanged (5.04 vs 4.99 s). An env-level regression (kernel/cuDNN/numpy) would have slowed this pass too. It didn't.
  • Hardware throughput parity: crediting the recompute forward (×4/3), the async trainer does 270.6 effective TFLOPS vs 265.0 pre-sync — the GPUs are working exactly as hard (+2%); the reported metric drops purely because its factor-3 convention books recompute as overhead.

Root cause 2 — wait_time_ratio and the two pipelines

Async pair: generation got faster (v0.5.15 engines) so idle wait shrank (28.2→18.7 s, helped by −6.4 s preprocess inside the wait), while train grew (recompute) — ratio 0.605→0.452. Trainer utilization went up and end-to-end step_time still fell 13%: the trainer was never the bottleneck in this pipeline, so honoring recompute cost almost nothing end-to-end. OPD pair: generation-side wait is unchanged (11.6≈11.8 s — teacher-scoring pipeline didn't speed up), so the +2.0 s of recompute passes straight through to step_time (+2.2 s = the entire “+13% rollout_time” flagged in §3). Same cause, different exposure.

Are the metrics computed correctly? Yes — nothing to fix. actor_train_time is a direct wall-clock measurement and actor_train_tok_per_s is real goodput (useful tokens per second) — both report the recompute cost honestly, because you genuinely produce 25% fewer trained tokens per second with full recompute on. actor_train_tflops uses the fixed-3 MFU convention on purpose: it answers “how much useful model compute per second”, which is the right number for comparing training configurations. The only usage rule it imposes: when two runs differ in recompute settings, their MFU numbers are measuring different workloads — multiply the recompute-on side by 4/3 (the HFU view) to compare hardware utilization, which is what shows the 270.6-vs-265.0 parity above.

Root cause 3 — the async data_preprocess drop (7.0 → 0.6 s)

Timer scope and the fetch/H2D code path are line-identical pre/post sync, and the OPD pair — whose reference ran on a July torch-2.11 env — shows no difference (1.03 vs 1.02 s). The 7 s belongs to the June-era reference stack (torch 2.9.1, transformers 4.x, older ray): the image-heavy DP shard's serialization/cross-node object transfer was simply slower two env generations ago. Attributed to the stack refresh, not to a sync code change; not worth deeper root-causing (it is a win, and the current stack is the one we keep).

Knob decision (recorded in follow-ups): the recipes ran fine for months without recompute at 4k response length, so dropping --recompute-* would reclaim ~25% trainer speed — but it buys almost nothing end-to-end where the trainer isn't the bottleneck (async), and costs the memory headroom the flags were meant to provide. Recommendation: keep recompute (honored semantics), treat reported actor_train_tflops across the sync boundary as non-comparable, and compare the recompute-corrected number instead.

Appendix — how activation recomputation actually works

Backprop needs each layer's forward-time inputs: for y = W·x, the weight gradient is dL/dW = dL/dy · xᵀ — you cannot compute it without x, and nonlinearities similarly need their forward values. The default is to keep every layer's interior activations (QKV projections, attention output, the 3×-wide MLP intermediate, norm inputs, …) alive from forward until backward consumes them — roughly tens of bytes-of-hidden-width per token per layer. For this 8B run (36 layers × 16,384 tokens/GPU × 4096 hidden × ~20× multiplier, bf16) that is an 80–100 GB-class activation footprint: activations, not weights, are what explodes with context length.

no recompute:    F1 F2 … F36 | B36 B35 … B1        all 36 layers' interiors held until used
full recompute:  F1 F2 … F36 | (F36↩→B36) … (F1↩→B1)   store only per-layer inputs;
                                                     re-run layer i's forward just before B_i;
                                                     one layer's interior alive at a time

Cost accounting (1F = one forward's FLOPs): forward = 1F; backward = 2F (each forward matmul has two same-sized backward matmuls, dx and dW — irreducible). No recompute: 3F. Full recompute: 1F + (1F re-forward + 2F) = 4F → time ×4/3, which is exactly the measured ×1.32. The flags: granularity full = whole layers (vs selective = attention interiors only — note FlashAttention already recomputes its own interiors, so on this stack full's savings come mainly from MLP/norm/projection tensors); method uniform + num-layers 1 = a checkpoint every single layer (maximum memory savings, full 4/3 cost). Pre-sync these runs fit in H200 memory at 4k response length without any of this — which is why the silently-dropped flags went unnoticed and the old runs were 33% faster on the trainer.

5 · Fully-async admission metrics — the accepted_staleness family

Definitions (examples/fully_async/fully_async_rollout.py::_build_staleness_metrics, logged once per rollout step by the collector):

The cold-start cohort wave. At t=0 the worker launches its entire active window at once — rollout_batch_size × prefetch = 128 prompt groups, all conditioned on weight version 0. The fast prompts of that synchronized wave finish first and feed the trainer a surplus of ready batches (train_wait ≈ 2 s at steps 1–13 vs 10–20 s in steady state), so the weight version advances every ~45 s. Meanwhile the wave's long-tail prompts — slowest exactly at step 0, when the untrained model writes its longest, most-truncated responses — are still decoding on v0–v2. By the time they complete, the current version is 4–7, their staleness is 3+, and the admission gate recycles them en masse: over_cap peaks at 0.54 around step 5. Once the original cohort drains, launches are naturally staggered (one new launch per completion), only the individually-slowest generations straddle >2 updates, and the ratio settles into the noisy 0–0.2 band. This is a one-time synchronization artifact of startup, not drift.

Why train_time is unaffected. The admission gate decides which groups fill the batch, never its size or token budget: every step trains exactly rollout_batch_size groups under the same --max-tokens-per-gpu 16384 dynamic batching, so per-step train compute is invariant to recycling. The cost of an over-cap storm lands elsewhere — as discarded sampler decode (the recycled groups' generation work) and, when supply is tight, as trainer wait. During this particular storm supply was anything but tight (the wave surplus kept train_wait at ~2 s), so the spike is invisible in every trainer-side timing metric — exactly as designed.

The full causal chain (each layer verified in code)

layerwhat happens
L1 · objectiveThis recipe is pure distillation (task reward is telemetry-only). Teacher scoring emits per-token k1 = log q_old − log p_teacher (_compute_topk_reverse_kl, Top-2+Rest approximation) shipped to the trainer as sample.opd_reverse_kl.
L2 · injection — the weak pointapply_opd_kl_to_advantages is one line: advantages[i] = adv − opd_kl_coef·reverse_kl (coef 1.0, per-token, detached, no clamp anywhere; this run has normalize_advantages=False). PPO's eps_clip bounds the probability ratio side only — advantage magnitude passes through untouched.
L3 · early-era baselineStudent is farthest from teacher at cold start: k1/max is 27–33 nats/token on every step 13–23 — tokens the teacher prices at e−30 are always present, not just at the spike.
L4 · the trigger batchStep 17's distinction is outlier mass: k1 mean 0.84 = 4× neighbours — moving a 512-sample mean that far takes whole trajectories, not stray tokens. And that batch's task reward was the window's highest (0.719): these were correct answers in a style the 30B-Thinking teacher dislikes. A pure-distillation objective presses on task-correct trajectories exactly as hard — that is its nature, not a bug.
L5 · gradient formationPer-token pg gradient scales with |advantage|: one 31-nat token contributes like 31 ordinary tokens; thousands of 4×-elevated tokens stack into a 470 pre-clip global norm. pg_loss/reverse-KL spike in lockstep (same source); ppo_kl/clipfrac barely move (the ratio side is guarded by eps_clip).
L6 · application & recoveryclip_grad=1.0, and the steady pre-clip norm is mean 0.84 / p95 1.04 — half of normal steps already clip. The spike step's parameter displacement is therefore exactly ordinary-sized; its direction is the batch's true objective gradient, merely low-SNR (dominated by few trajectories). Aftermath: no NaN, ppo_kl peak 0.017, all series back in band within ~10 steps, endpoint parity with the reference to the third decimal.

Class vs instance. Which early batch draws a disagreement-dense trajectory cluster is sampling luck — 470@17 (new) vs 232@7 (reference) are two rolls of the same die. The class is deterministic (guaranteed by L1–L3); the instance is random.

Severity assessment

regimeverdict
current config (rollout-q_old, staleness cap 2)benign cold-start transient; zero damage (endpoint parity is the proof)

Mitigation options and trade-offs

  1. Per-token k1 winsorization (clamp to ±K nats before advantage injection) — kills the class at the source; an e−30 token keeps its gradient direction, only the magnitude is capped; small, documentable bias. Pick K from the observed k1 distribution (p99), not by fiat.
  2. Coefficient warm-up (ramp opd_kl_coef over the first ~30 steps) — covers precisely the max-distance era; simplest; no steady-state protection.
  3. normalize_advantages=True would suppress outliers automatically but changes the objective's semantics — that is a different experiment, not a fix.
  4. Keep clip_grad=1.0 as the backstop it already is.

Recommendation: leave the frozen baselines untouched (their value is comparability). If the wide-staleness direction (m12 follow-on) restarts, do (1) first with (2) alongside — in that regime this class stops being a one-off transient and becomes daily weather.

One-line verdict: the spike is the inevitable product of an unclamped heavy-tailed estimator meeting a disagreement-dense batch — currently caged by grad clipping and mild conditions. The cage is real; remember what lives inside it.
